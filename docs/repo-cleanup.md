# Repo-wide cleanup plan

Readability, then optimizations and bug fixes.

Read every `.m` file in the repo and clean it in place — better names, complete header docs, consistent conventions and formatting, reflowed long lines. The first phase of this operation is **behaviour-preserving**: no output changes, a constraint that is **mechanically checkable**, so the diff does not need to be trusted, only verified. **Four stages of change**, defined fully in section 3. Stage 1 and Stage 2 are the behaviour-preserving readability pass. Stage 3 is the structural cleanups and optimizations it deliberately deferred, done once the readability pass is complete and committed. Stage 4 is the bugs found along the way — each recorded with a severity the moment it is found, each left unfixed until last, kept in their own stage so a bug list never gets lost inside a cleanup list.

**How this document is executed, whichever model opens it.** Whoever reads this is the **orchestrator**, not the editor. Do not clean any file yourself. Every unit of work here — each Stage 1/2 tranche in section 4.1.2, each Stage 3 item in section 0.3, each Stage 4 bug in section 0.4 — names the subagent that executes it, and the orchestrator's whole job is to dispatch that unit to that agent with the Agent tool, in plan order, one at a time, then check what comes back before dispatching the next. The agent's definition fixes its model and reasoning effort, so the right model gets used regardless of which model is driving the session. The Agent tool can override `model` per call but **not** `effort`, which cuts both ways: pass `model: "sonnet"` explicitly to `matlab-cleanup-mechanical` because frontmatter alone has been seen failing to downgrade it, and pass no `model` at all to the three opus agents so their frontmatter `effort` survives. **A dispatched agent is a worker and never spawns a subagent of its own** — section 4.1.2 records what happened here when one did. Section 4.1.2's dispatch contract lists what every dispatch must carry, because the subagent starts with none of this context. The orchestrator holds the plan, sequences the work, keeps the user informed, and never accumulates a tranche's worth of someone else's code in its own context.

Reverse-rename check: clean a file (renames, header, reflow), then undo the rename map on the canonical form of the new file and assert it's identical to the canonical form of the old one:

```matlab
c_new = canon(new_file);
for k = 1:size(renames,1)   % renames = {new_name, old_name}
    c_new = regexprep(c_new, ['(?<![A-Za-z0-9_.])' renames{k,1} '(?![A-Za-z0-9_])'], renames{k,2});
end
isequal(canon(old_file), c_new)   % must be true
```

The lookahead `(?![A-Za-z0-9_])` matters: without it a short name can wrongly match inside a longer one. This repo has several live instances of that trap — `dwell` inside `dwell_tot`, `dwell_raw`, `corr_dwell`, `d_dwell`, `f_corr_dwell`; `pupil` inside `pupil_raw`, `pupil_dil`, `pupil_sz_mean`, `mean_pupil`; `scan` inside `scan_pre`, `scan_post`, `scan_all`, `d_scan`, `d_tot_scan`; `fix_x` inside `fix_x_bin`; `gaze_x` inside `gaze_x_bin` and `gaze_x_this`; `err` inside `err_this`, `d_err`, `avg_d_err`. The rename map itself must be a bijection with disjoint domain/range — assert this before using it:

```matlab
dom = renames(:,1); ran = renames(:,2);
assert(numel(unique(dom)) == numel(dom));
assert(numel(unique(ran)) == numel(ran));
assert(isempty(intersect(dom, ran)));
```

| **1** | Comments, header docs, whitespace, **operator and bracket spacing, indentation**, reflow, blank-line grouping, file-local renames, **triaging commented-out code (verdicts only, no deletion)** | empty (after reverse rename) | `isequal` — fully automatic, no execution |
| **2** | Adding a suppressing `;`, preallocation, `find`→logical indexing, deleting a provably unused assignment | non-empty but must match a whitelisted pattern | pattern check **plus** runtime golden output |
| **3** | Signature changes, adding `arguments` blocks, merging duplicate functions, reordering statements, changing accumulation order in a float reduction, anything touching the RNG stream, **acting on the Stage 1 triage of commented-out code** | — | **not part of the behaviour-preserving pass** — reviewed and done individually, once Stage 1/2 is done |
| **4** | **Bug fixes** found anywhere during 1/2/3, each carrying a severity | — | not mechanically checkable; reviewed and fixed individually, **last** |

Semicolon insertion is Stage 2, not A: `tree2str` preserves display-vs-suppress, so the canonical diff is exactly `X` → `X;` — trivially whitelisted, but not invisible.

**Why bugs get their own stage rather than sitting inside Stage 3.** A bug list buried in a cleanup list gets lost: Stage 3 is 13 structural items and the bugs are 23, so under the old three-stage shape this document's "next step" was two-thirds bug report by count and read as neither. Splitting them also fixes the ordering — a bug fix that lands before a related structural change is more likely to be clobbered or duplicated by it, so Stage 4 runs after Stage 3 is settled, not alongside it.

**Every Stage 4 item carries a severity, and the severity decides only the order the list is worked in — never whether the bug is recorded or whether a tranche stops for it.**

| severity | marker | meaning |
|---|---|---|
| highest | 🔴 | Silently wrong results on a path that has actually been run — published numbers may be affected. |
| middle | 🟠 | Reachable, but not silent: it errors out, or it only touches plots, logging, or display. |
| lowest | 🟡 | Latent — not reachable with the current config or inputs, but would bite a plausible future use. |

An emoji rather than an inline colour, on purpose: GitHub and most previewers strip inline `style` attributes, but they all render emoji, so the marker actually shows up everywhere instead of degrading to plain text on the harder renderer.

Stage 3 matters most. The tempting changes are all Stage 3 (see section 0.3's list). Every one of them changes output, call sites, or validation behaviour, so none of them belong in the behaviour-preserving pass — keeping them out is what makes that pass's diff skimmable instead of line-by-line. They are the next step of the same overall cleanup, not abandoned.

**Commented-out code is not a delete item, and the work splits across two stages, not within one.** Someone put those 181 lines there on purpose and the purpose is often still live, so **keeping is the default**. Triage — reading each block, working out what it was for from the code around it rather than from `git log`, and writing one verdict per block: *superseded*, *scaffolding*, *alternative*, *unfinished*, or *unknown* — is Stage 1's step 2c, done inline as each file is touched. Only the follow-through, acting on that verdict table by actually deleting or converting a block, is Stage 3. An honest *unknown* costs a few commented lines, while a wrong *superseded* destroys the only copy of something, because code that was written commented-out has never been live and so is nowhere in the history to recover from. Items 0.3.4 (the triage, done, its table now in section 4.1.3 per step 2c) and 0.3.4b (the follow-through, pending, section 0.3).

In this repo the temptation is unusually strong, and worth naming explicitly so it can be resisted: 2704 of the 4300 lines are near-duplicate boilerplate that is *obviously* mergeable, and the merge would cut the repo by roughly a third in one commit. Do not do it during Stage 1. It is item 0.3.1, done after the readability pass, with individual review — because the six copies have quietly diverged (`dummymode` differs, `screenNumber` differs, the drift-correction call is commented out in some and not others, `free_view_exp.m` alone uses a `'data/'` subdirectory prefix), and a merge has to decide each of those. That decision is invisible to `canon` and cannot be checked mechanically.

When the pass uncovers a *bug* — and it already has, twenty-two times over, see section 0.4 — **record it in the findings list first with its severity**, so the recording survives even before the fix happens; the fix itself comes later, as a Stage 4 item. Four of the twenty-two are 🔴, meaning they silently corrupt numbers that have already been published, and the pull to fix them the moment they are found will be strong. Resist it: a bug fix in the middle of a Stage 1 tranche makes that tranche's `check_tier_a` fail, and a failing check that is *expected* to fail is worthless as a check. Recording an 🔴 does not interrupt the tranche in progress; it only moves that item to the head of the Stage 4 queue.

Statement reordering is kept out of Stage 1/2 even though it looks cosmetic, purely because the check cannot distinguish a safe reorder from an unsafe one — it gets the same individual review as the rest of Stage 3.

**The one binding change every later tranche must follow: the rename map is a function of the file, and the checker call changes shape.** The map is `map = renames(file)`, taking the path (or bare filename) of the file being checked and returning only the rows that apply to it. Note `renames('<new>')`, not a bare `renames`. **Why the map has to be per-file, which is the decision behind everything else in this entry.** `check_tier_a` reverse-substitutes every **new** name it finds in `canon(new_file)` back to the corresponding old name. A row is therefore unsafe in any file where its new name already exists as a *different* identifier, because the substitution rewrites that innocent identifier too and the comparison fails for a reason that has nothing to do with the edit. This repo has four live instances, all of them in the section 4.1.1 table: `n_trials` is the new name for `nTrials` in `saccade_exp.m`, `saccade_lr_exp.m`, `free_view_exp.m` and `saccade_setup.m`, but is already a distinct variable in `spem_exp.m:21`, `spem_measures.m:3` and `free_view_measures.m:3`; `phase_x`/`phase_y` are the new names for `phaseX`/`phaseY` in `spem_solo_exp.m:303-304` but are already variables in `spem_exp.m:312,381`; `idx_pre`/`idx_post` are the new names for `idxPre`/`idxPost` in `spem_analyze.m` but already exist in `free_view_analyze.m:18-19`; and `screen_width_px`/`screen_height_px` are the single new names for three different old spellings living in three different files (`screen_w`/`screen_h` in `+lib/preprocess_gaze.m:43` and `pre_process.m:27`, `screenWidth`/`screenHeight` in `free_view_exp.m:334`, `screen_width`/`screen_height` in `free_view_measures.m:9-10`). A flat repo-wide map cannot express that four-spellings-into-two merge at all, since it is many-to-one; scoping by file makes it expressible and makes the other three safe. The reverse worry — an **old** name appearing inside a string literal, which `canon` does not strip, such as the `'!V TRIAL_VAR index %d'` messages in four of the `*_exp.m` files versus `V` in `preprocess_gaze.m:124` — turns out not to matter at all, because the substitution only ever searches for new names. **Rule 1, binding: within one file, at most one row per old name.** Where an old name means two different things in the same file, only **one** cluster of sites is renamed and the other sites keep the old name; reverse substitution then still reconstructs the original exactly, and a single map row suffices. Three sites in this repo need this, and the tranche that owns each file must rename only the cluster named here: `i` in `+lib/preprocess_gaze.m` is the correspondence-point loop at line 132 (renamed to `i_point`) and the animation-frame loop at line 240 (**left as `i`**); `k` in `free_view_analyze.m` is the session-member loop at line 115 (**left as `k`**) and the matched-pair loop at line 167 (renamed to `i_pair`); `gap` in `free_view_analyze.m` is the undefined-before-use read at line 67 (**left as `gap`**, and it is bug 0.4.6) and the duration-to-days chain at lines 248-335 (renamed to `session_gap_days`). **Rule 2, binding: within one file, at most one row per new name.** Two old names cannot merge into one new name inside a single file, because the reverse substitution would not know which old name to restore. **One genuine collision was surfaced by transcribing the section 4.1.1 table and is resolved here rather than quietly:** the table maps both `hcb` and `cb` to `h_colorbar`, and both live in `free_view_analyze.m` — `hcb` is the handle returned by `colorbarpzn` at lines 288, 346, 360, 377, 596, 638, 657, 672, and `cb` is the handle returned by the builtin `colorbar` at lines 95, 333, 615.
